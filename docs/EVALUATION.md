# 评测

Biny 使用确定性检查验证实现行为，使用独立模型评测观察任务质量。二者的输入、成本和结果含义不同，界面体验还需要人工确认。

## 实现检查

在仓库根目录使用：

```bash
pnpm typecheck
pnpm lint
pnpm test
pnpm build
```

`pnpm test` 包含标准测试与端到端测试。端到端入口会先构建 CLI；`pnpm build` 同时构建 CLI 与 Desktop。聚焦某个行为时，可先运行覆盖该行为的具体测试文件。

这些测试使用本地文件、数据库、子进程和协议替身覆盖行为。它们通过不代表真实服务商可用，也不证明模型在任意项目中能正确完成任务。

## 内置模型评测

```bash
biny eval run --label baseline --out baseline.json
biny eval compare baseline.json candidate.json
```

评测运行使用实际模型配置，会发起模型请求并产生相应用量。`--task` 可选择指定任务；比较要求两份真实报告，不用预期结果代替。

执行前固定模型、端点协议、思考配置、步数与费用预算、工作区、记忆策略及 verifier。隔离会话与记忆，避免前次运行内容影响新结果。随机性较大的任务需要重复运行，并保留每次原始输出与状态。

## 工具预选消融

在开发仓库中运行：

```bash
pnpm exec electron benchmarks/tool-preselection.mjs /absolute/new-output-dir 3
```

该入口使用当前聊天模型和指定辅助模型（省略时取自动选择的首个可用配置），比较每回合辅助预选与基础/历史工具加按需 ToolSearch。使用真实模型请求、48 个合成扩展工具和工作区 Read，覆盖基础读取、新能力发现、历史复用及有依赖的工具调用。每次独立会话，关闭记忆和技能，交替运行顺序；仅模拟外部业务数据，不访问真实 MCP 服务。凭据通过 Electron 的既有存储读取，不写入报告或修改用户配置。

输出保留任务、源码摘要、原始模型输出、工具审计及逐回合 verifier。成功要求执行预期调用并给出正确答案，不能只依据模型的 completed。统计任务成功率、从回合开始到首个主模型请求的延迟、搜索次数和主/辅助模型合计 token；缺失用量保留未知。Provider 缓存和网络波动未被控制，小样本结果不能直接外推到其他模型、目录或 Code Mode。

## 工具结果处理对照

```bash
pnpm exec electron benchmarks/tool-result-optimization.mjs /absolute/new-output-dir
```

使用当前聊天模型、相同 Read 工具和固定合成文件，对照直接调用与允许 `run_script` 的模式。覆盖记录搜索、日志汇总和多文件聚合；模型自主决定是否使用脚本。每题两种模式各运行一次，交替顺序、隔离会话与记忆，最多 6 步、12 次工具调用、每题 120 秒。凭据通过既有存储读取，不写入报告。

输出任务和源码摘要、调用记录、独立答案判定、每次请求用量和累计上下文文本字节数。总 token 包含脚本生成；缺失用量保持未知。单次样本、自动路由端点和未控制的 Provider 缓存不能证明普遍收益，也不能换算成账单节省；RTK 的命令执行需另行验证。

## Terminal-Bench

仓库提供 [Harbor 接入说明](../scripts/evals/harbor/README.md) 与相应 adapter。Harbor 管理任务环境，官方 verifier 检查实际产物；Agent 回答文本不参与最终通过判定。

使用时需具备 Harbor、Docker 和对应模型凭据。服务商密钥留在环境或私有文件中，报告只保留脱敏配置。任务环境安装、网络、超时和 verifier 失败与模型未完成任务分别记录。

历史例子见 [DeepSeek V4.1 Flash 评测报告](eval/terminal-bench-2.1-deepseek-v4.1-flash-biny.md)。该报告记录指定日期和配置下的运行，不是当前版本自动继承的成绩。

## 成绩口径

| 结果 | 能说明什么 |
| --- | --- |
| Pass@1 | 每题首次符合口径的有效运行结果。 |
| 重跑通过 | 后续尝试达到 verifier 要求，需单独标注次数。 |
| 多轮并集 | 至少一次通过的覆盖情况，不能当成单轮 Pass@1。 |
| 环境或 verifier 失败 | 该次运行缺少有效任务判定，不能伪装成测试通过。 |
| 模型报告完成 | 模型的语义判断，仍需外部证据确认。 |

比较策略时保持其他变量一致，按需要做消融。一次 API 成功、一个例子或更高的多轮并集不能单独证明代码改动提升了质量。

## 结果交付

报告写明运行配置、任务版本、预算、原始产物位置、退出状态、verifier 证据与未验证范围。聚焦测试、完整测试、构建、真实模型请求和人工界面验收分别报告。

Desktop、TUI 和浏览器交互通过人工步骤检查。非界面协议测试与构建可以作为实现证据，不能替代实际窗口、系统权限和输入法体验。

## 工具选择评测结果

2026-10-19 · 最终修正版 v3.1 · Luna low

本轮中文样本中，工具模型的首次选对率高于 BM25 和改写＋BM25，但 token 和费用也更高。网关限流分布不均、中文标签未经独立人工复核，结果还不足以证明稳定替代。

### 测试方式

- 工具模型：Biny 的模型 ToolSearch 读取目录，返回最多 20 个候选，再由 Luna 选择一个工具。
- BM25：原始请求做关键词检索，返回最多 20 个候选，再由同一 Luna 选择。
- 改写＋BM25：Luna 将请求改成英文检索词，再做 BM25 检索和 Luna 选择；合法空改写回退原始请求。
- 全目录直接选择：仅在 20 工具时，将全部工具直接交给 Luna。

固定 `codex/gpt-6-luna`、Responses API、`low`。200 个保留任务族，每族英文、中文直述、中文语义改写三种表达，覆盖 33 个来源；每条表达均配有移除标注目标的条件，共 8,400 试次。20/1,000 是目录规模，20 是候选上限。正例目录预置标注目标，不衡量从全量语料筛到 1,000 工具的能力。

只评分第一次业务工具名；不执行工具、不检查参数、不循环重试，结果不是任务完成率。独立原始响应审计核对 8,400 条，评分差异为 0。Jev 本轮未运行。

### 与参考项目的关系

- [ToolDiscoveryBench](https://github.com/SarathChandraBellam/ToolDiscoveryBench/tree/cb23a85eab5eed452fa0b47b2d20ddb7e96b9e0d)：参考首次工具选择、拒选、延迟和费用的分开报告方式。
- [toolhunch](https://github.com/dfm88/toolhunch/tree/8373a8b7c21d9e93b9f5c39ea4dce5b29a30bf2e)：参考单轮直接选择与检索后选择的对照方式。本轮使用 ToolRet 相关性标签，“相关工具”不保证是多步骤任务的首个可执行工具。

这是自建对照实验，不能当作两个项目的官方成绩或严格复现。中文为扩展样本；本轮采用 Responses/low；BM25 不包含 toolhunch 的 embedding＋RRF 混合检索，也未运行 Codex、Claude Code 原生产品。

### 成本和限制

- 381 个最终试次遭遇网关限流：工具模型 34、BM25 64、改写＋BM25 228、全目录 55；全部保留在主分母。因此差异同时包含算法与服务可用性的影响。
- 533 次正式/修正请求缺少用量或费用，`≥` 表示已知下限。费用按公开标价估算，网关实付未知。token 和耗时包含辅助模型及最终选择，按有目标/移除目标各半平均；索引初始化另计。
- 改写结果跨目录和正负条件复用；每题归属一次改写成本，耗时为实测改写与检索/选择耗时相加，并非连续端到端测量。
- 工具模型读取整个目录，1,000 工具时输入显著增多。BM25 无候选时跳过最终模型，所以低费用也伴随更多未选择。
- 中文由同一 Luna 起草，没有独立人工复核；公共相关性标注不完备。本轮只跑一次，不宣称普遍优越性。

本节仅发布最终修正版结果；不包含旧实验、原始请求、网关配置或本机路径。
