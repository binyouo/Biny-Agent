# 开发与文档规范

本规范说明 Biny 如何维护功能事实、检查修复范围、处理故障与资源边界，以及沉淀开发经验。开发环境与测试命令见[贡献指南](../CONTRIBUTING.md)，功能说明见[文档索引](README.md)。

## 一个事实只维护一处

每个行为域由一份所属专题文档维护。专题按职责组织，可以跨越多个模块；其他页面通过链接引用，不复制同一份契约。首页和索引只保留必要概览。

专题说明以下与该功能有关的内容，不要求每页套用固定模板：

- 职责与边界：用户能完成什么，哪些工作由其他模块负责。
- 状态与事实来源：谁拥有写入权，哪些数据持久化，哪些状态只是可重建的展示。
- 真实运行路径：从用户或外部入口到结果，经过哪些关键模块；失败、取消和恢复如何影响结果。
- 验证入口：相关源码、具名符号、测试或命令，以及仍需实际环境确认的边界。

链接源码文件和具名符号，避免复制易变的实现细节或依赖行号。阅读文档后仍需核对当前源码；列出测试入口不代表测试已经通过。

职责、接口、状态转换、运行路径、兼容规则或失败行为发生变化时，同一变更更新所属说明。仅改变内部组织、没有改变这些契约的重构无需修改说明。期望行为与实现不一致时，先说明差异，不能直接把实现现状写成预期。

当前行为与提案分开描述。计划放在对应 Issue 或 PR，确定后的稳定行为再并入所属专题。新增公开页面更新文档索引和 `.gitignore` 的明确放行名单；本地规格、参考笔记和运行日志不随之公开。

本地子系统只在 `docs/specs/features/README.md` 登记契约归属和对应实现说明；每个子系统一个 owner 页面。跨模块关系通过链接说明，不在父页或客户端页重复维护子系统状态机。公开功能专题解释使用与工作方式，不复制本地登记表；实现笔记不能另设一套期望行为。

## 可执行检查

- `pnpm check:docs` 从项目首页、贡献指南和公开文档索引检查可达专题中的本地链接、Markdown 锚点，以及行内标注的 `src/`、`tests/`、`scripts/`、`config/`、`docs/` 路径；代码块示例不作为真实文件清单，不访问外部网站。
- `pnpm check:docs:local` 在上述范围之外检查本地规格入口、功能契约与实现笔记，并要求子系统名称和契约入口不重复、每行恰有一个 owner、功能页及实现页全部登记。缺少本地规格时报错，不静默跳过；历史任务记录和模板不参与当前契约检查。
- `pnpm check:boundaries` 解析并在内存中打包本地运行时依赖：Renderer 及其可达源码不得依赖 Node 内置模块或 Electron；核心 Agent、Runtime、Session、Tool、Permission、LLM 不得反向依赖 Desktop、TUI 或 CLI；TUI 展示组件不得依赖检查器列明的执行、持久化模块及文件、进程、网络能力。纯类型引用不产生运行时依赖；TUI 的纯路径和平台信息适配仍允许。检查不执行应用、不写构建产物。

`pnpm check:project` 运行检查器的临时项目回归测试、依赖边界与公共文档检查，并接入 CI 的静态检查任务。本地规格继续被 Git 忽略，CI 不要求不存在的私有文件，也不能证明云端任务已经读过本地契约。

这些检查证明登记、引用和可静态解析的本地运行时依赖关系，不证明文案语义没有重复、代码遵守所有行为契约或运行时安全。动态构造的导入路径、第三方包内部和系统副作用仍须审查与行为测试；权限拒绝、writer 所有权、恢复去重等由所属真实入口测试保护，界面仍需人工验收。

## 沿完整链路检查修复

从报告中的操作入口和前置状态出发，确认预期结果，再追踪输入、关键调用、状态读写和副作用，直到用户或调用方能观察到的结果。单个函数通过测试不能证明真实入口已接入该修复。

修改判断、标识、数据结构或时序时，检查依赖它的调用方、相邻分支、持久化副本和同类入口。属于同一缺陷的情况一并修复；无关问题单独记录，不扩展为全仓清理。例如，模型选择写入的标识改变后，需要同时检查恢复时的读取和客户端展示。

验证从能覆盖目标行为的最小稳定入口开始。改变跨模块装配、协议、持久化或恢复语义时，检查真实装配链路；已有测试能覆盖时复用，有缺口再补。回归测试须在旧行为下因目标缺陷失败，并在修复后通过；编译或装配错误不能证明捕获了缺陷。

交付说明触发条件、修复前后可观察的变化、实际验证范围与未验证边界。详细测试约定和命令见[贡献指南](../CONTRIBUTING.md#行为变更)。

## 故障与资源边界

以下约束用于相关实现与审查，不表示现有模块已经逐项通过验证；检查时仍需沿实际入口确认。

- **读取失败不是空数据。** 区分不存在、合法空值、读取失败、内容损坏与格式不支持。失败时保留原数据，不以空列表、默认值或较旧格式冒充成功，也不据此覆盖文件。已有只读快照可保留，但须说明其过期或未知状态；权限、额度等控制数据无法确认时，拒绝依赖它的操作，不能借旧快照放行。
- **外部格式以实际契约为准。** 导入数据、修改其他程序的配置或适配协议时，核对官方类型、文档或真实序列化样本中的字段类型、单位、默认值与失败表示，不能仅凭字段名推断。已知错误在适配边界按契约转换，保留未知错误，不把鉴权失败、额度耗尽、限流和取消归为同一种可重试故障。
- **异步结果属于发起它的操作。** 根据实际边界使用请求标识、会话或账号身份、版本等检查结果归属；切换、取消、清空或释放后的迟到结果不能覆盖新状态。全局忙闲不等于某次请求的成功或失败。超时、信号与退出码等独立事实分别保留，不能仅凭退出码为零认定正常完成。
- **清理必须到达停稳状态。** 创建进程、后台任务、定时器、订阅或注册项的所有者负责释放；取消信号发出不等于工作已经结束。需要等待的清理须等待退出或排空，并使迟到通知失效；等待设置明确的超时和失败结果。一个清理回调失败不能阻止其他独立资源释放，错误须报告，不能把未清理完毕写成成功。
- **测试占用的资源由测试收回。** 配置、会话、文件和端口使用独立的临时目录或动态分配的命名空间，不接触日常数据与凭据。失败、重试或超时后同样停止并等待派生进程和后台工作，恢复被修改的进程级状态，再移除临时资源。并行时发生的资源冲突与测试结束后的写入应追查所有权，不能仅因单独运行通过就归为环境抖动。隔离入口见[贡献指南](../CONTRIBUTING.md#验证入口)。

## 经验先积累，再形成长期规则

一次失败先在对应 Issue、PR 或本地维护记录中保留可核对的证据：版本或提交、触发条件、实际问题、缺失的验证，以及能防止复发的改进。私有数据和凭据留在本地；公开记录使用脱敏材料。

同一事件的多次更新不算多个独立案例。只有反复出现的独立案例说明现有约定不足，或一次事件已经明确暴露权限、数据丢失等严重风险时，才考虑形成长期规则；不按固定次数自动升级。

新增规则前，先检查已有条款能否澄清或合并，或问题是否更适合用回归测试、静态检查解决。规则写清适用场景、保护的结果和证据出处，不把单次修复步骤变成所有任务的必经流程。

维护相关规则时复核其前提。实现、工具或使用方式已经改变，规则重复，或执行成本超过其防护价值时，缩小范围、合并或删除。删除时说明原风险由什么覆盖；风险仍存在且没有替代保障时保留。
